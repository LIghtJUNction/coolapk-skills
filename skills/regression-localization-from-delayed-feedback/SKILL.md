# 用版本时间线定位回归

## 适用情形

用户在较晚更新后报告功能失效，但问题可能早已出现。反馈延迟会让“更新后坏了”看起来像一次新回归，导致排查从错误版本开始。

## 记录版本与证据

收到报告时，先把事实和回忆分开记录：

1. 记录当前异常版本，以及用户最后记得功能正常的版本；标明这是记忆、日志还是实际复测结果。
2. 询问首次发现异常的时间范围、近期更新记录和可稳定复现的条件。
3. 尽量准备可比较的旧版本与新版本，在相同条件下复测，并记录每次结果。
4. 若旧版本也失败，继续向更早版本回溯；找到正常与异常版本的边界后，再缩小检查范围。
5. 将结论写成“最后已知正常版本”“首次已知异常版本”及其证据，避免仅凭一次回忆定因。

## 案例启示

原帖作者描述：一名用户起初将故障归因于最近一次更新。作者让用户测试旧版本后发现旧版也无法使用，随后继续测试了二十多个测试版，最后发现该功能在约两个月前的版本中已经失效；用户也承认记不清具体何时开始出问题。

这是一个延迟反馈导致错误回归判断的个案，不应推广为用户通常会记错。它说明回归定位需要验证版本边界，而不是直接把当前报告时间当作故障起点。

## 记录模板

- 最后已知正常版本：版本号或“未知”；证据及日期：
- 首次已知异常版本：版本号或“未知”；证据及日期：
- 首次发现异常时间：精确日期、范围或“未知”；信息来源：
- 复现条件与结果：
- 测试过的版本及逐版结果：
- 当前结论与仍未确定之处：

原帖未提供应用具体版本号、功能名称或测试版清单，不应补造这些信息。
