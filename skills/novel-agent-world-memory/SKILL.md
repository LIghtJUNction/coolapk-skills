# 小说 Agent 的世界记忆与关系图

## 预算：先估算记忆需求

设计小说 Agent 时，应先比较作品所需记忆与模型可用的上下文预算。上下文预算还要为当前提示、生成内容及其他任务留出空间；不能把模型窗口大小直接当成可用于小说记忆的容量。

原帖用一部长篇中文小说作示例：按 446.52 万字乘以作者假设的 0.6，算术结果为 267.912 万 tokens。0.6 只是原帖采用的假设，不是通用中文分词比率，也不是实测 tokenizer 结果。实际估算应使用目标文本及目标 tokenizer 核算。

原作者在 2025-09-25 列过若干模型窗口数字，作为当时的举例保存：GPT-4 为 8,192 tokens，GPT-4（32k）为 32,768，GPT-5 系列为 128,000，Gemini-2.5 Flash/Pro 为 1,000,000。它们未经核实，不能视为官方规格，也不能用于当前规划。具体型号 ID、访问端，以及输入与输出预算均未交代。

## 持久世界记忆：把世界表示为关系图

以图作为持久世界记忆。实体表示人物、地点、物品、组织等对象；事件和实体之间的关系表示为边。事件不作为实体保存。边既可表示具体事件，也可表示抽象关系，例如朋友、母亲或成员关系。

实体和边都不删除。事件一旦发生就进入历史；世界状态的变化通过追加信息表达。即使角色忘记某件事，也把“忘记”表示为新事件，保留原事件。实体或关系永久改变时，同样追加变更记录，而不抹去既有历史。

实体以 UUID 标识并记录类型；边另有自己的 UUID。属性按名称组织，并保留按时间排列的多个版本。新增属性时，先确认是否已有表达同一概念的属性键：有则追加该键的属性值版本；没有则新增键和值。属性值带有 `timestamp_desc`，用自然语言描述其在故事历史中的时间位置，以便定位和比较变化。属性分类保持灵活，避免任意类型值造成混乱，也避免固定字段限制不同题材。

## 监督变更：只接受合理的世界更新

Agent 提出的图变更须经过监督，以维护剧情连续性。原帖提出两种监督方式：由人检查，或由另一个 Agent 检查。可以将两者视为同一变更审核流程的不同执行者；审核的目标是判断新增实体、边和属性版本是否符合现有世界记忆。

机械规则自动验证在原帖中被认为难以充分解决该问题。无论采用人工还是另一 Agent，核心约束仍是通过追加变更保存历史，并检查新信息与已有记录的关系。

## 具体表示：数据结构与图操作

酷安转载文字选用 Python 和 NetworkX；对应博客另展示两条 uv 命令。整理时补上进入新项目目录的步骤，避免把依赖装到当前其他项目：

```sh
uv init PlotWeave
cd PlotWeave # 整理补充的工作目录步骤
uv add networkx
```

博客代码使用 `networkx.MultiDiGraph` 管理图：节点以 UUID 为键并附带实体对象；边以边自身的 ID 作为 key，并附带边对象。添加实体时检查重复 ID，添加边前检查两端实体存在。多重有向图允许同一对节点之间存在多条边，并保留边的方向。

属性值的具体结构为 `AttributeValue(value: str, timestamp_desc: str)`。原帖概述的实体属性形状为 `dict[str, list[AttributeValue]]`；边采用相近的建模方式。自然语言时间描述由创作系统根据剧情记录提供，原帖没有规定解析、排序或校验格式；不能把 timestamp_desc 当成已经标准化的时间戳。

这里的“追加历史”是设计约定，不是所示 Python 类型自动提供的不可变性保证。`dataclass` 未设 `frozen`，属性使用可变的 `dict` 与 `list`；调用方仍可能修改或删除其中的数据。整理建议：需要在实现中以受控写入接口、存储层约束或审计机制落实追加约定。

## 实现缺口：明确尚未解决的部分

原帖指出，简单模糊查询效果可能不佳，并将向量搜索列为需要较大改动、当时尚待实现的部分。没有给出向量索引、检索流程或评测结果，因此这些内容不能当作已经完成的功能。

这两篇早期文章展示设计和部分代码片段，单凭转载文字不能组装出完整工程。对应博客另链接 [PlotWeave 项目仓库](https://github.com/shadow3aaa/PlotWeave)，可取得实际项目文件；本文没有运行项目，也未审查后续版本的持久化、向量检索或完整审核实现，不能把早期计划状态当成仓库至今没有这些功能。两篇材料未给出可复现的一致性和生成质量评测。
