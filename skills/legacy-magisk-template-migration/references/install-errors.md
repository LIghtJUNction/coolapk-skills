# 定位 Magisk 模块安装错误

安装日志中的单条提示通常只能指出失败阶段，不能单独证明根因。先保留完整日志、确认 ZIP 来源和文件是否完整，再根据最后一个成功阶段缩小范围。

## 按提示定位阶段

- `Copying zip to temp directory` 是复制阶段的进度提示，本身不代表失败。应查看它之后是否出现明确错误，以及复制是否继续完成。
- `Invalid Uri` 表示文件 URI 或路径解析阶段有问题；它不证明某一种固定根因。
- `Cannot copy to cache` 指向复制到缓存阶段。
- `Unzip error` 指向解压阶段。

后三类错误只能帮助定位阶段，不能据此断定缓存分区损坏，也不能认定重启一定能解决。检查日志后续内容、文件管理器提供的路径、ZIP 是否可正常读取，以及安装器报告的具体错误，再决定下一步。

若提示 `This zip is not a Magisk Module!`，检查下载文件是否确为模块安装包、压缩包是否完整，以及包内安装器结构是否符合所用安装方式。若提示要求更高 Magisk 版本，应核对模块要求和设备当前版本；旧帖关于特定版本分区异常的推断不是通用结论。

## 安装完成后继续验证

“刷入成功”只说明安装流程报告完成，不能证明模块功能已经生效。检查 Magisk 模块列表中的启用状态、重启后的实际行为，以及模块自身日志或功能结果。若问题只在一个模块出现，优先核对该包及其适用条件；若多个模块都失败，保留日志并逐项排查共同环节。

旧帖建议删除整个 `/data/adb`、替换 Magisk 核心 BusyBox 或重刷 Root；这些会影响其他模块或系统状态，不是通用诊断步骤，因此不作为排障操作提供。帖中提到的 `/data/adb/Models` 大小写和拼写与官方 `/data/adb/modules` 不符，不可照此路径操作。旧文关于模块数量和 120 秒启动时限的说法没有足够依据，不作为限制。
