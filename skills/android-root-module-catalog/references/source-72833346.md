# Aether_OptExt 线程分配模块：构建和规则

这是一个 Rust 编写的 Android 线程分配模块。原帖希望按线程名称和 CPU 集群性能类型分配线程，以改善能效；效果、兼容性和耗电变化尚未独立实测。来源：[酷安技术文章](https://www.coolapk.com/feed/72833346)；[项目源码与可能的发布文件](https://github.com/NetizenNemo/Aether_OptExt)。原帖声明只供学习参考，修改和分发前应查看项目当前许可与作者要求；项目地址未验证当前可用性。

## 构建、安装与观察

准备 Rust、Android NDK，并设置 `ANDROID_NDK_HOME`；在项目根目录执行：

```sh
rustup target add aarch64-linux-android
python build.py
```

帖子所述产物是 `out/Aether-OptExt_YYYYMMDD_HHMMSS.zip`，可在 Magisk 或 KernelSU 中安装。配置位于 `/sdcard/Android/Aether/threads.json`，日志为 `/sdcard/Android/Aether/threads_log.txt`，自动分配缓存位于 `/sdcard/Android/Aether/threads_cache`。日志中的“新应用”据称表示发现未配置线程，“已绑核”表示绑定成功；应结合设备实际状态确认。

## 规则与拓扑

`features.ebpf` 控制 eBPF，`features.auto-for-none` 控制未知应用自动分配缓存。每条 `rules` 使用 `friendly`、`packages` 和 `cpuset`；`cpuset.other` 是默认核心范围，`cpuset.comm` 把核心范围映射到线程名模式。例如原帖用 `6-7` 对应 `UnityMain`、`UnityGfxDeviceW`，用 `0-5` 对应 `NativeThread*` 和其他线程。数字只是示例，设备的核心编号和大小核布局可能不同。

对于同一线程，原帖描述以权重最高的规则为准：精确匹配为 1000 加模式长度，字符范围为 500 加非通配符数，`?` 为 300 加非通配符数，`*` 为 100 加非通配符数，进程级空匹配为 200。应按实际权重计算，而不是简单假定星号规则总高于兜底。

原帖列出 `4+3+1`（默认）、`3+4+1`、`4+4`、`6+2`、`2+6`、`4+2+2`、`4+3+2+1` 预设，声称安装时自动识别拓扑。未知应用线程按名称估算负载并缓存：`RenderThread`、`UnityMain`、`GLThread*`、`Vulkan*` 和 `CodecLooper`、`Video*`、`Audio*` 分配大核；`Worker*`、`Job*`、`Thread-*`、网络、后台及未匹配线程分配小核。缓存按包名去重并过滤部分系统包，模块更新时旧缓存会清除。线程名是启发式线索，并非负载测量。

## eBPF 与回退

原帖描述模块监听 `sched/sched_process_exec` tracepoint，将新进程 PID 写入 BPF HASH map，再由主循环读取；列出的内核选项为 `CONFIG_BPF_SYSCALL=y`、`CONFIG_BPF_EVENTS=y`、`CONFIG_KPROBE_EVENTS=y` 和 `CONFIG_PERF_EVENTS=y`。帖子称部分使用 Android Vendor Hooks 的内核可能限制高级功能，此时回退到 `/proc` 轮询；这些均为项目作者的描述，纳秒级写入和实际性能未获独立验证。
