# Android 全量 AOT 编译与残留包排查

原帖在努比亚 Z60 Ultra 的类原生系统中使用一个 KernelSU / Magisk WebUI 模块。正文没有给出模块确切名称和下载 URL；不能把别的同类模块冒充为原帖项目。

## 编译步骤与观察

1. 按原帖安装模块后，在 Root 管理器中打开它的面板。
2. 先选 `verify`，范围设为第三方应用，检查日志是否正常完成并显示 `Success`。
3. 此步无异常后，再切换面板的“全量”模式，范围扩展到系统与第三方应用。
4. 持续看日志、可用存储与设备温度。原帖提醒编译阶段 CPU 占用、功耗较高；其建议插电、可用时启用旁路供电并辅助散热。

`verify` 与界面的“全量”是不同选择。原帖没有公开后者映射的具体 ART compiler filter，不将它补写为某条 `cmd package compile` 命令。

| 作者报告 | 边界 |
|---|---|
| 全部完成耗时 20 多分钟 | 单个设备案例，不是其他手机的预计时长 |
| 存储占用从 166G 到 190G | 相差约 24G，计量口径与应用集合未给出 |
| 应用更新后仍需重新编译 | 不将一次全量编译视为永久覆盖所有后续版本 |
| 冷热启动和能耗改善 | 原帖的解释与体验，没有受控性能或耗电对照 |

## 编译中断：无法定位应用包

原帖遇到旧的随机包名 SukiSU 安装残留。它结合安装历史和日志定位目标，再在 Termux 中进入 Root shell 查询 APK 路径。

以下将原帖随机包名泛化为“包名”；必须替换为日志中已确认的目标：

```sh
su
pm path 包名
```

没有返回路径是该案例中的排查线索，不应单凭任意空输出就认定一个包可删除；包名、用户和安装状态仍需核对。

原帖随后卸载确认的残留包，命令模板如下；这是卸载操作，会影响指定目标：

```sh
pm uninstall 包名
pm uninstall --user 0 包名
```

其案例中第一条返回 `Success`，第二条显示未安装，然后回到面板继续编译。这个结果不能推广成所有卸载故障的恢复方法。
