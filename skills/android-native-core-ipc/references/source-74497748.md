# Native Bridge 加载与回调契约

[酷安文章](https://www.coolapk.com/feed/74497748)介绍了 Android Native Bridge 的插件化接口，并提出用桥接库转发特定原生库加载请求的思路。Native Bridge 框架提供接口；跨架构指令翻译由具体实现承担。原帖以 x86 环境加载 ARM 库和 `libhoudini.so` 为例。适用场景和加载时机取决于系统及实现，不能把“原生加载失败后一定调用桥接”当成所有系统版本的保证。

桥接实现导出 `NativeBridgeItf` 回调表；系统通过接口请求加载库和获取 trampoline（可调用入口）。原帖提出按路径筛选目标，使用 `dlopen` 加载，再依据句柄和符号名使用 `dlsym` 查找入口，并提醒检查 SELinux、加载器命名空间、文件权限和回调重入。目标库必须满足实际 ABI、函数签名和调用约定；直接返回符号地址并不能自动解决架构转换、JNI 调用或命名空间兼容问题。

## 原帖示例的 ABI 问题

原帖 Rust 片段是构想而非可直接使用的实现。对照 [AOSP 当前 Native Bridge 头文件](https://android.googlesource.com/platform/art/+/refs/heads/main/libnativebridge/include/nativebridge/native_bridge.h)：

- 当前 `initialize` 接收 runtime callbacks、私有目录和指令集三个参数；原示例声明成无参数函数。
- 当前 `getTrampoline` 接收句柄、符号名、shorty 和长度四个参数；原示例缺少长度。头文件还指出 v7 起使用另一入口。
- 回调结构必须按目标 Android 版本的完整字段顺序、签名和布局实现；原文把一些回调直接排在 `isSupported` 后，不能据此声称与 AOSP 对齐。
- `OnceLock<NativeBridgeCallbacks>` 的内存布局不能当成系统期望的 `NativeBridgeCallbacks` 对外静态对象；示例也没有证明其初始化会在系统读取该符号之前执行。

因此不要复制该片段声称可以编译使用；先对照目标版本的 AOSP 头文件实现 ABI 和初始化，再在受控设备上验证生命周期、错误处理及兼容性。原帖提出中后期应用加载时机限制和 UID 阈值，但缺少可复现环境，不能推广为系统通则。
